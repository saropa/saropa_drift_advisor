# BUG: `assets/web/bundle.js` is a committed generated artifact with no staleness gate anywhere

**Status: Open**

Created: 2026-09-02
Component: CLI (build/publish pipeline)
File: `scripts/modules/web_assets.py`, `.github/workflows/publish.yml`, `.github/workflows/main.yaml`, `.husky/pre-commit`
Severity: Performance / Correctness (ship-wrong-code risk) — High

---

## Summary

`assets/web/bundle.js` is generated by `npm run build:js` from ~60 TypeScript modules, committed to git, published to pub.dev, and served to **every** browser and VS Code webview. Its sibling generated file `assets/web/style.css` is guarded by three independent sync gates. `bundle.js` is guarded by none — no pre-commit check, no CI check, no publish check, no `publish.py` step. A `.ts` edit committed without running `npm run build:js` ships a stale viewer to pub.dev and to the jsDelivr CDN fallback, with no error anywhere.

---

The pre-commit hook covers Dart formatting and extension TypeScript only:

```bash
grep -n "has_staged" .husky/pre-commit
```

```
if has_staged '\.dart$'; then
if has_staged '^extension/.*\.tsx?$'; then
```

`assets/web/*.ts` matches neither pattern — the hook prints *"No staged extension .ts files — skipping TypeScript and build checks"* and lets the commit through.

**Emit site(s):** absence of a gate — `scripts/modules/web_assets.py:22` (CSS-only constant), `.github/workflows/publish.yml` (CSS-only verify step), `.husky/pre-commit` (no `assets/web` branch).

## Steps to Reproduce

1. Start from a clean tree at `v4.2.5`.
2. Edit any web-viewer source, e.g. change a string in `assets/web/utils.ts`.
3. Do **not** run `npm run build:js`.
4. `git add assets/web/utils.ts && git commit -m "test"`.
5. Observe the hook output, then push a `v*` tag to run `.github/workflows/publish.yml`.

---

## Expected Behavior

Some gate — pre-commit, CI, publish workflow, or `scripts/publish.py` — rebuilds `bundle.js` and fails if the committed copy differs from the build output, exactly as it already does for `style.css`.

---

## Actual Behavior

The commit is accepted with `No staged extension .ts files — skipping TypeScript and build checks`. CI (`main.yaml`) runs only `flutter pub get / analyze / format / test` — no npm step at all. `publish.yml` runs `npm ci && npm run build:style` and then verifies **only** `assets/web/style.css`. `scripts/publish.py` calls `ensure_web_assets_sync()`, which is CSS-only. The stale `bundle.js` is published to pub.dev and becomes the `@v4.2.5` jsDelivr artifact that mobile hosts load when they cannot resolve the package root.

---

No error is produced anywhere — that is the defect. The publish succeeds and the viewer silently runs old code.

## Regression Info

- Last working version: never gated.
- First broken version: whenever `assets/web/*.ts` + esbuild replaced the hand-written `app.js` (the `bundle.js` outfile predates 4.2.5).
- What changed: the CSS gate was written when SCSS was the only generated web asset; the JS gate was deferred in a comment and never revisited.

---

## Root Cause

`web_assets.py` was written for a single generated asset (`style.css`) and the module docstring records the intent to extend it to `.ts` "in future". The web bundle was later added as a second generated asset without extending the gate, and neither the pre-commit hook's staged-file patterns nor CI were updated.

---

## Impact

- **Who is affected:** every consumer of a release published from a tree with an unbuilt `bundle.js` — pub.dev users, the jsDelivr CDN fallback path used by Flutter mobile hosts, and the VS Code panel (which reads the same asset).
- **What is blocked:** any web-viewer fix, including the escaper fix in `bugs/004_web_viewer_xss_esc_missing_quote_escaping.md`, can be authored, reviewed, merged and released without ever reaching users.
- **Data risk:** indirect — a security fix in `assets/web/` that never reaches the shipped bundle leaves the vulnerability live while the changelog claims it is fixed.
- **Frequency:** every commit that touches `assets/web/*.ts` without a manual rebuild.

---

## Fix Sketch

1. Extend `scripts/modules/web_assets.py` with `BUNDLE_JS = os.path.join(ASSETS_WEB, "bundle.js")` and a `check_bundle_js_sync()` that builds to a temp outfile with the exact `esbuild.config.mjs` options and byte-compares — mirroring `check_web_assets_sync()`. Wire it into `ensure_web_assets_sync()` so `publish.py` covers both artifacts.
2. Add the CI/publish step next to the existing CSS verify:

   ```yaml
   - name: Build web assets (TS → bundle.js)
     run: npm run build:js
   - name: Verify web bundle in sync
     run: |
       if [ -n "$(git status --porcelain assets/web/bundle.js)" ]; then
         echo "::error::assets/web/bundle.js is out of sync with assets/web/*.ts. Run 'npm run build:js' and commit bundle.js."
         exit 1
       fi
   ```

3. Add a `.husky/pre-commit` branch for `has_staged '^assets/web/.*\.(ts|js)$'` that runs `npm run build:js` and fails if `bundle.js` is dirty but unstaged. Keep it out of the extension branch — the two trees have different toolchains.
4. Extract the esbuild option object from `esbuild.config.mjs` into a shared module so the gate and the build cannot drift apart (single source of truth).
